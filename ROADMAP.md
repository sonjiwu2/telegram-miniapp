# RESHALA — ROADMAP

Социальное развлекательное Telegram Mini App: рулетки, споры, голосования, AI-вердикты для компаний друзей.

Статусы: `TODO` → `IN PROGRESS` → `DONE`. Каждый этап завершается прогоном typecheck/lint/test/build и остановкой до команды «дальше».

## Этап 1 — Project foundation — DONE

- Next.js 16 (App Router) + TypeScript strict
- Tailwind CSS 4
- Prisma 7 + PostgreSQL (schema/config, без данных)
- Zod-валидация env
- Базовая структура каталогов
- Тема (light/dark, синхронизация с Telegram theme params)
- Telegram WebApp bootstrap (ready/expand, без auth)
- Dev-режим (`npm run dev`)
- lint/typecheck/test/build

## Этап 2 — Telegram auth — DONE

- Валидация Telegram initData (HMAC-SHA256 по официальному алгоритму) на сервере
- Модель `User` в Prisma, upsert по Telegram ID
- Auth-слой: подписанная httpOnly-сессия (свой HMAC-формат, без внешних JWT-либ), `POST /api/v1/auth/telegram`, `GET /api/v1/me`
- DEV auth bypass (`{"dev": true}`, работает только при `ALLOW_DEV_AUTH=true`, физически запрещён в production через `env.ts`)
- Security-тесты: подпись initData (валидная/поддельная/просроченная/подменённые поля/отсутствующий hash), сессия (валидная/подменённая/просроченная/битый формат)

## Этап 5 — «Кто сегодня?» — DONE

- `POST /api/v1/sessions/:id/participants` — ручное добавление участников
  создателем (без Telegram-аккаунта у самих участников), только до старта
- `POST /api/v1/sessions/:id/finalize` — идемпотентная финализация: победитель
  вычисляется криптографически стойким `crypto.randomInt` строго на сервере
  до анимации; повторный вызов не пересоздаёт результат (защита от гонки —
  через уникальный индекс `Result.sessionId`, а не блокировки)
- `resolveRoulette` — чистый резолвер, покрыт тестами (победитель всегда из
  списка участников, sanity-check распределения по многим прогонам)
- UI `/who-today`: шаблоны вопроса + свой вариант, участники (добавление/
  удаление), анимация рулетки (с `prefers-reduced-motion` фолбэком —
  показывает результат сразу), экран результата, «Реванш» (новый независимый
  раунд) и «Новый вопрос»
- Сознательно не делал (см. раздел 6 ТЗ): несколько победителей за раз,
  веса участников, «иммунитет», сохранённые шаблоны в БД — это заявленные
  PRO/будущие механики, не MVP

## Этап 9 — Голосование (Poll) — DONE

- Модель `Vote` (`@@unique([sessionId, userId])` — один голос на пользователя;
  повторный голос меняет предыдущий — upsert, allowVoteChange включён
  по умолчанию, без отдельной настройки)
- `POST /api/v1/sessions/:id/vote` — только для `POLL` в статусе `OPEN`,
  проверяет что вариант принадлежит сессии
- Подсчёт голосов — часть общего диспетчера финализации: `resolvePoll`
  (обёртка с `prisma.vote.groupBy`) + чистая `computePollResult` (тестами
  покрыты победитель/ничья/нулевые голоса/один вариант) — тесты сразу
  поймали баг: нормализация нулевых `counts` случайно оказалась только
  в обёртке, а не в чистой функции, из-за чего `payload.counts` не включал
  варианты без единого голоса
- Кто за что голосовал — никуда не отдаётся, наружу только агрегированный
  `payload: {counts, totalVotes, tie}` в `Result`, и только после финализации
- **Важное архитектурное решение**: в отличие от «Кто сегодня»/«Нам похуй»
  (где решение принимает один человек локально), в голосовании участвуют
  МНОГИЕ пользователи по ссылке — поэтому основной UI живёт не на `/poll`
  (это только форма создания), а на уже существующем `/s/[id]` (Этап 7):
  создатель после создания редиректится туда же, куда попадают
  проголосовавшие по share-ссылке
- `/poll` — вопрос + варианты → создаёт `POLL`, добавляет варианты, стартует,
  редиректит на `/s/[id]`
- `PollView` (`src/components/sessions/poll-view.tsx`) — голосование
  (кнопки-варианты, смена голоса), для создателя — `ShareActions` (иначе
  ссылку неоткуда взять) и «Завершить и посмотреть результаты»; после
  `RESOLVED` — прогресс-бары с процентами
- deadline и настройки anonymous/public voters/show-results-before-vote
  сознательно не делал — не в MVP-списке раздела 59, полноценная реализация
  каждой добавляет отдельный пласт UI/логики

## Этап 11 — AI-архитектура + AI Вердикт — DONE

- `AIProvider` — провайдеро-независимый интерфейс (`src/server/ai/types.ts`),
  конкретная реализация `AnthropicAIProvider` через `@anthropic-ai/sdk`
  (`messages.parse()` + `output_config.format: zodOutputFormat(...)` —
  структурированный JSON-ответ вместо парсинга текста руками)
- `getAIProvider()` — фабрика с кэшем; если `AI_PROVIDER`/`AI_API_KEY` не
  заданы в `.env` — фича просто выключена (`503 AI_NOT_CONFIGURED`),
  остальное приложение AI не требует
- `AIRequest` — модель аудита обращений к AI (провайдер/модель/статус/
  латентность, БЕЗ содержимого промпта) — используется и как основа
  дневного лимита бесплатных вердиктов (`AI_VERDICT_DAILY_FREE_LIMIT = 3`,
  вынесен в `src/config/limits.ts`)
- `resolveAiVerdict` встроен в существующий диспетчер `RESOLUTIONS`
  (`session-repository.ts`) как ещё один `SessionType` — без параллельной
  инфраструктуры: проверка «минимум 2 кандидата» сделана опциональной,
  т.к. у AI Вердикта этого понятия нет
- Система тонов (`src/lib/ai/tones.ts`) — 8 тонов («Судья», «Сарказм»,
  «Бабушка» и т.д.), тайп-гард `isAiTone`, дефолт «Судья»
- Безопасность: `buildVerdictSystemPrompt` жёстко запрещает реальное
  насилие/травлю/унижение защищённых групп/юридические-медицинские
  вердикты; отказ модели (`stop_reason === "refusal"` или её собственное
  `refused: true`) рендерится ФИКСИРОВАННОЙ фразой нашего компонента, а не
  тем, что ответила модель — так решение об отказе контролирует код, а не
  формулировка LLM
- `/ai-verdict` — тон-чипы, textarea с ситуацией, карусель «думает»-фраз
  на время ожидания, таймаут финализации 45с, читаемые русские сообщения
  об ошибках (лимит/не настроено/таймаут), экран результата с `ShareActions`
- `/s/[id]` и `/r/[id]` (публичный OG-результат) — отдельная ветка рендера
  для `AI_VERDICT` через переиспользуемый `VerdictSummary` (без хуков —
  рендерится и на сервере, и на клиенте); заголовок OG-картинки берёт
  headline вердикта вместо «победителя»
- Осознанно отложено: стриминг ответа модели (вердикт короткий, ждать
  недолго), сохранение истории собственных промптов пользователя (лишний
  риск приватности, не в MVP-списке)

## Этап 12 — Споры + AI-судья — DONE

- `Option` переиспользован как «сторона» спора: `label` — имя стороны,
  новое поле `argument` — её аргумент (для остальных типов сессий всегда
  null) — без параллельной модели, та же generic Session/Result-инфраструктура
- Создание: заголовок спора + 2-6 сторон (имя + аргумент), выбор режима
  решения (раздел 8 ТЗ): «Голосование людей» или «AI Судья»
- **Голосование** — полностью переиспользует инфраструктуру POLL
  (`resolvePoll`/`castVote`/upsert-голос = смена голоса до закрытия):
  `resolveDebateVote` оборачивает `resolvePoll` и добавляет `verdictLine` —
  случайную (crypto.randomInt, не Math.random) фразу из безопасного набора
  шаблонов, а не сгенерированный текст
  - Таймер голосования (5 мин/30 мин/1 час/24 часа/без таймера,
    `settings.durationMinutes`) — сервер реально запрещает новые голоса
    после истечения (`castVote` → `409 DEBATE_CLOSED`); фоновых джоб в
    проекте нет, поэтому фактическое закрытие (`finalize`) триггерит
    клиент создателя, когда таймер долистал до нуля — сознательный
    компромисс без cron-инфраструктуры
- **AI Судья** — `resolveDebateJudge`: сторонам присваиваются буквы
  (A, B, ...) вместо настоящих internal id при обращении к модели —
  модель никогда не видит и не может подделать реальный cuid; ответ
  строго JSON `{winnerId, headline, reasoning, sentence, confidence}`
  (раздел 10 ТЗ), сопоставление буквы обратно с опцией — на сервере
  - Дневной лимит и аудит (`AIRequest`) теперь общие для AI Вердикта
    и AI-судьи — вынесены в `src/server/ai/rate-limit.ts`
    (`assertWithinDailyAiLimit`/`recordAiRequest`), `resolveAiVerdict`
    переведён на тот же хелпер; лимит переименован в
    `AI_DAILY_FREE_LIMIT` (был `AI_VERDICT_DAILY_FREE_LIMIT`)
  - Те же тона и правила безопасности (раздел 11-12 ТЗ), что и у AI
    Вердикта: отказ на реальном насилии/травле/юридических-медицинских
    темах рендерится фиксированной фразой кода, а не текстом модели
- `/debate` — форма создания (стороны, режим, тон/таймер), `DebateView` —
  единый компонент для голосования и AI-судьи, всех статусов (голосуем →
  результат с процентами / ждём AI → вердикт с уверенностью в %)
- `/s/[id]` — новая ветка рендера для `DEBATE`. `/r/[id]` изменений не
  потребовал: у спора есть `winnerOptionId` (в отличие от AI Вердикта),
  поэтому общий `getWinnerLabel`/`SessionResultSummary` уже показывают
  имя победившей стороны корректно
- Осознанно отложено: реальное серверное автозакрытие по таймеру без
  участия клиента (нет фоновых джоб/cron в проекте — общее архитектурное
  ограничение, не специфичное для этого этапа)

  как и голосование, это интерактивная фича только для `/s/[id]`
- **Достижения** (раздел 21 ТЗ) — вычисляются на лету по существующим
  таблицам (`GET /api/v1/achievements`), без отдельной таблицы прогресса:
  - «Жертва системы» — выпал в рулетке 5 раз
  - «Невезучий» — выпал два раза подряд (сравнение последних 2 закрытых
    рулеток, где участвовал пользователь)
  - «Демократ» — проголосовал 50 раз
  - «Создатель проблем» — создал 20 споров
  - «Мне реально похуй» — создал 25 сессий «Нам похуй»
  - «Судья Дредд» — создал 10 AI Вердиктов
  - Список отображается в `/profile` (разблокированные выделены,
    остальные приглушены)
- **Сознательно не реализованы 2 из 8 титулов раздела 21**: «Народный
  любимец» (выиграл 5 голосований) и «Вечно прав» (3 AI verdict победы
  подряд) — оба требуют привязки стороны спора/варианта к конкретному
  аккаунту, а сторона `DEBATE` сейчас это просто текст (`Option.label`)
  без `userId`. Реализовать по-честному — значит переделать ввод сторон
  спора так, чтобы сторона могла быть привязана к реальному участнику
  (как `SessionParticipant` в рулетке), а не свободным текстом — это
  отдельный, более крупный редизайн Этапа 12, не тянущий на этот этап
- **Streaks (раздел 22, «можно добавить»)** — не реализованы: в ТЗ прямо
  помечено как опциональное дополнение («не делать агрессивным», «не
  присылать guilt notifications»), а push-уведомлений в проекте нет
  вообще (не отдельный этап плана) — добавлять company-streak без
  возможности его анонсировать пользователю малополезно
